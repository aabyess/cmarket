## 0. 변경 개요

이번 브랜치는 `next-intl`(v4.13.6) 기반 다국어 라우팅 인프라를 도입:
- 모든 `app/` 라우트를 `app/[locale]/...` 하위로 이동 (파일명은 그대로, 경로만 이동)
- `i18n/routing.ts`, `i18n/request.ts`, `i18n/navigation.ts` 신규 추가 (locales: `ko`(기본, 접두사 없음) / `id` / `en`)
- `middleware.ts`에 `next-intl` 미들웨어 통합, 기존 인증/역할 기반 리다이렉트 로직을 로케일 인지형으로 수정
- `components/commons/LanguageSwitcher` 신규 추가 (Sidebar, 로그인 페이지, Admin 레이아웃에 배치)
- `messages/{ko,en,id}.json` 신규 추가

## 2. 발견한 문제 목록

### 🔴 중요 (Important)

**[I1] `messages/*.json`에 실제 UI 텍스트가 거의 없음 — 언어를 바꿔도 화면 텍스트는 그대로 한국어**
- 파일: `messages/ko.json`, `messages/en.json`, `messages/id.json`
- 재현 조건: `LanguageSwitcher`로 English/Bahasa Indonesia 선택 → URL은 `/en/...`, `/id/...`로 바뀌지만 대시보드/폼/버튼 등 화면 텍스트는 전부 한국어 그대로 노출됨
- 원인 추정: 세 파일 모두 `Common.appName`, `Common.languageSwitcher`, `Locales.{ko,id,en}` 5개 키만 존재. 코드 전체에서 `useTranslations`/`getTranslations`를 사용하는 곳은 `components/commons/LanguageSwitcher` 단 한 곳뿐(grep 결과, `features/`, `app/[locale]/`, 나머지 `components/` 전체에서 0건). 즉 이번 브랜치는 라우팅 인프라(URL 로케일 접두사, 미들웨어, 언어 전환 UI)만 구축했고, 실제 화면 콘텐츠 번역은 아직 연결되지 않음.
- 참고: 커밋 메시지가 "Phase 1"이라 의도된 범위일 수 있으나, 사용자 입장에서는 "언어를 바꿨는데 아무것도 안 바뀌는" 상태로 보이므로 머지 전 의도된 범위인지 확인 필요.

### 🟡 사소 (Minor)

**[M1] 이동된 파일 4곳의 라인1 경로 주석이 마이그레이션 이전 경로를 그대로 가리킴**
- 파일:
  - `app/[locale]/(main)/buyer/loading.tsx:1` → `// app/(main)/buyer/loading.tsx`
  - `app/[locale]/(main)/seller/loading.tsx:1` → `// app/(main)/seller/loading.tsx`
  - `app/[locale]/(main)/support/loading.tsx:1` → `// app/(main)/support/loading.tsx`
  - `app/[locale]/admin/loading.tsx:1` → `// app/admin/loading.tsx`
- 원인 추정: `git mv` 방식 이동 후 CLAUDE.md 컨벤션(파일 1행 경로 주석)을 갱신하지 않음. 기능에는 영향 없음.

**[M2] 루트 `app/not-found.tsx`가 없어 로케일 세그먼트 밖에서 발생하는 404는 커스텀 스타일 없이 렌더링됨**
- 근거: `pnpm build` 출력에 `○ /_not-found  0 B  114 kB`가 `app/[locale]/not-found.tsx`와 별개 라우트로 생성됨. `app/[locale]/layout.tsx`(폰트, `NextIntlClientProvider`, 전역 CSS 포함)는 `[locale]` 세그먼트 하위에만 적용되므로, 미들웨어 matcher를 벗어나거나 로케일 세그먼트에 매칭되지 않는 요청은 Next.js 기본 404(스타일/폰트/Provider 미적용)로 폴백함.
- 재현 조건: 이론상 발생 가능한 경로이며, 실제로 트리거되는지는 브라우저 검증 필요(정적 분석 한계).
- 개선 방향: `app/not-found.tsx`(루트, `[locale]` 밖)를 최소한의 안내 페이지로 추가하는 것을 권장.

**[M3] `pnpm lint`가 `.next/`, `public/pdf-worker/*.mjs`, `next-env.d.ts`를 lint 대상에서 제외하지 않음**
- 파일: `eslint.config.mjs`
- 이 브랜치가 만든 문제는 아니지만(기존부터 있던 설정 공백), 로컬에서 `pnpm build` 후 `pnpm lint`를 돌리면 수천 건의 무관한 경고가 쏟아져 실제 lint 신호를 가리는 구조. CI에서 build 캐시가 남아있는 상태로 lint를 돌리는 경우 동일 문제가 재현될 수 있음.

## 3. 회귀 의심 지점 (아직 문제는 아니지만 위험해 보이는 곳)

**[R1] `middleware.ts`의 `splitLocale()`이 URL 접두사만으로 로케일을 판단, `next-intl`의 쿠키(`NEXT_LOCALE`)/`Accept-Language` 기반 감지와 별개로 동작**
- 위치: `middleware.ts:11-18` (`splitLocale`), 이 값이 인증 관련 리다이렉트(`/login`, role 기반 홈 이동)의 로케일 접두사 결정에 사용됨
- 시나리오: 사용자가 이전에 언어를 English로 바꿔 `NEXT_LOCALE=en` 쿠키가 저장된 상태에서, 접두사 없는 보호 경로(`/buyer/dashboard`)에 비로그인 상태로 접근 → `splitLocale`은 접두사가 없으므로 무조건 `ko`로 판단 → `/login`(접두사 없음, 한국어)으로 리다이렉트됨. `next-intl` 자체 미들웨어였다면 쿠키를 참고해 `/en/login`으로 보냈을 가능성.
- 영향도: 기능이 깨지진 않음(로그인은 정상 동작), 다만 사용자의 언어 선호와 리다이렉트 대상 언어가 어긋나는 UX 불일치 가능성. 실사용 빈도가 낮은 edge case로 판단되어 심각도는 낮게 책정.

**[R2] 인증 미들웨어가 `handleI18nRouting(request)`을 우회하는 raw `NextResponse.redirect` 다수 사용 (`middleware.ts:71,93,98,103,107,111`)**
- 현재는 문제 없음(리다이렉트 목적지 URL 자체에 `withLocale()`로 로케일을 미리 박아 넣으므로 요청을 다시 받을 때 정상 처리됨)을 코드 추적으로 확인. 다만 `next-intl`이 리다이렉트 시점에 추가로 설정하는 로케일 쿠키(`NEXT_LOCALE`) 갱신 등의 부수효과는 이 경로들에서 발생하지 않음 — 향후 `next-intl` 버전업 시 이 우회 경로가 조용히 로케일 동기화를 깨뜨릴 수 있는 지점이므로 주시 필요.

**[R3] `messages/*.json`이 5개 키뿐인 상태로 향후 화면별 번역 키가 대량 추가될 예정이라면, ko/en/id 3파일 동기화를 수동으로 유지해야 함**
- 현재는 키 개수가 적어 3파일이 완전히 동일(diff 없음, 검증 완료)하지만, 앞으로 키가 늘어나면서 파일 간 diff가 벌어질 위험. 키 파리티를 검증하는 스크립트/린트 규칙이 없음.
